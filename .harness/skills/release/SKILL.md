# Release workflow

Use to prepare or publish a version, recover a failed release, or verify delivered packages. Inputs: requested action, version/tag, target commit and publication scope. Resolve the selected checkout through the local-context reader; preserve unrelated working-tree changes.

1. Read [release policy](../../../CONTRIBUTING.md#releases), [release guide](../../docs/release.md), [testing](../../docs/testing.md) and [validation limits](../../docs/validation.md). Confirm the repository is MatriQ/su03t-tools, identify the exact commit/tag, and inspect existing runs, draft/public release state and assets. Preparation or inspection alone does not authorize tags, pushes, workflow dispatches or publication; reuse publication authority already given by the user.
2. For a new version, reconcile Cargo.toml/Cargo.lock, the Mac bundle build number and the version-bound harness probe. Update installation/release notes and affected harness sources through [maintenance](../../docs/maintenance.md). Stage only the intended release changes; a tag releases its committed tree, not uncommitted files. Do not move an existing tag or replace published bytes to hide a fix.
3. Follow [verify](../verify/SKILL.md) for source checks and the installer/publisher suites. For packaging changes, verify real packages in temporary locations. Inspect the version-specific asset layout: macOS universal DMG from v0.6.2 (older versions use ZIP), Linux x86_64/ARM64 and Windows regular/portable x64 ZIPs from their documented versions. Retain checksum, executable version, architecture/signature, installer and desktop evidence. Cross-platform CI does not establish physical-board acceptance.
4. Within the requested publication scope, commit the reviewed release changes and publish the matching annotated vX.Y.Z tag using the [new-version procedure](../../docs/release.md#publish-a-new-version). Tag pushes trigger publication automatically. An existing-tag workflow dispatch can also publish; an empty tag builds artifacts only. Track the run for the selected tag and commit, including source checks and all four platform package jobs, before reporting publication.
5. For failure or an uncertain response, inspect that same run and release before retrying. The publisher verifies assets in a draft before publishing; an incomplete draft can resume, and a complete published release must be verified without replacement. The workflow retries publication at most four times with 20 seconds between attempts. Retry only a diagnosed transient or corrected failure using the original verified artifacts; stop on identity, permission, checksum or immutable-asset conflict and report the exact unresolved cause. Changed published bytes require a new version.
6. Follow [delivery inspection](../../docs/release.md#inspect-delivery) from the selected version's checkout. Compare tag commit, run revision, expected assets, manifest and packaged executable version; metadata --check-release validates that checkout's package version, not arbitrary latest main. Check the public installation path, including [Windows post-release verification](../../docs/release.md#windows-packaging), within the task's execution scope. Verify the separate Homebrew tap update before claiming Homebrew availability; a source Release does not prove the Cask updated. Use the [installation/recovery procedure](../../docs/release.md#installation-and-recovery) for app rollback; firmware rollback is separate hardware work.

Return the version/tag and commit, run and Release URLs, package/checksum results, public installer/Homebrew status and remaining acceptance limits. Distinguish prepared, built, published and verified states. Keep raw machine evidence in ignored local state and durable validation notes under .harness/docs/. This workflow never authorizes attached-device flashing, driver installation or clearing OS download protections.
